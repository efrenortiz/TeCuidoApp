# CareRequest — Security and Privacy Design

## 1. Purpose

Define the security and privacy considerations for Fase 5 without introducing a separate security architecture. The design reuses the authentication, authorization, storage, audit, and file-handling mechanisms already established in previous phases.

## 2. Authentication

All CareRequest creation operations require an authenticated actor.

The actor is taken from the authenticated application context and is never accepted as a freely selectable client field.

## 3. Authorization

Authorization is enforced server-side and follows ADR-004.

The operation distinguishes between:

- a patient creating a request for themselves;
- a responsible creating a request for an authorized patient.

When `responsible` is present, the service must validate an active and valid ResponsiblePatientRelationship for the target patient.

Client-side visibility or disabled controls are not authorization mechanisms.

## 4. Data minimization

CareRequest stores only the data required by the approved workflow:

- patient;
- created_by;
- optional responsible;
- doctor;
- clinic;
- selected slot start/end;
- motivo;
- optional padecimiento;
- optional descripcion;
- status;
- optional idempotency key;
- timestamps;
- optional Appointment relation.

No diagnosis, automated triage, clinical recommendation, or other derived clinical interpretation is generated by CareRequest.

## 5. File privacy

Attachments reuse the ClinicalDocument infrastructure from Fase 4.

Files remain subject to the existing private-storage and access-control rules of ClinicalDocument.

Fase 5 does not introduce a second file-storage mechanism.

The system must not expose storage paths or private file URLs directly as a substitute for authorization.

## 6. File limits

The Fase 5 attachment policy reuses the approved Fase 4 constraints:

- maximum 5 files per CareRequest operation;
- permitted file types: PDF, JPEG, PNG;
- maximum 10 MB per file.

No new file-type or size policy is introduced.

## 7. Antivirus

Antivirus scanning is explicitly outside the scope of Fase 5 and outside the scope of any project phase.

No ClamAV or other antivirus subsystem is introduced by this design.

## 8. Rate limiting

To reduce abuse, CareRequest creation is limited to:

**3 CareRequests per authenticated actor within a rolling 1-hour window.**

The counter is evaluated using PostgreSQL and the existing transaction/locking strategy.

No Redis, Celery, queue, or external rate-limit infrastructure is introduced.

A valid idempotent replay is resolved before applying the creation rate limit.

## 9. Idempotency security

The optional `Idempotency-Key` protects a CareRequest creation operation in the namespace:

`(created_by, idempotency_key)`.

The key is not reused as the Appointment namespace.

An identical replay returns the previously committed result; a conflicting reuse of the same key is rejected according to the API contract.

## 10. Transaction and rollback

The complete creation/conversion operation is executed inside one outer transaction.

If the operation fails:

- database changes roll back;
- the physical files created during that execution are compensated synchronously;
- the error is propagated.

A filesystem orphan-cleanup process is not part of the application. Any orphan cleanup is external operational maintenance performed by the system administrator.

## 11. Logging

Logs must not contain clinical free-text content or file contents.

Logging should prefer:

- actor identifier where already permitted by existing logging practices;
- CareRequest/Appointment identifiers when available;
- error class and operation context.

Do not log raw attachment contents, storage secrets, or private download URLs.

## 12. Privacy boundary

CareRequest is an administrative request mechanism. It does not perform automated clinical interpretation.

Any information entered into `motivo`, `padecimiento`, or `descripcion` is treated as sensitive clinical-context data and follows the existing application's authorization and privacy controls.

## 13. Reuse principle

Fase 5 must reuse existing controls from:

- ADR-004 authorization;
- Agenda Fase 2;
- ClinicalDocument Fase 4;
- existing audit/logging mechanisms.

No parallel security subsystem is introduced.

## 14. Administrator read access to sensitive clinical fields — scope decision (2026-09-18)

`requirements.md` §62 and `ADR-004-role-and-object-permissions.md` §8/§26 require that administrator access to sensitive clinical information be recorded in audit. `CareRequest.motivo`/`padecimiento`/`descripcion` are sensitive clinical-context data (§12 above) and are visible to a superuser through `CareRequestAdmin`'s read-only listing/detail views (the only administrative access surface Fase 5 introduces — no add/change/delete, per the hardening already closed in `phase-5-final-report.md` §30).

**Decision: deferred to Fase 6, not implemented in Fase 5.** Verified before deciding, not assumed:

- No `ModelAdmin` anywhere in the project — including the ones already exposing sensitive clinical content in earlier, closed phases (`ClinicalEncounterAdmin`, `MedicalRecordAdmin`, `PrescriptionAdmin`, `StudyOrderAdmin`, `ClinicalDocumentAdmin`) — records an audit event on read access. `medical_records.services.audit.record_event`/`safe_record_event` are invoked exclusively from application service-layer functions, never from `admin.py`.
- `docs/design/care-request-audit-and-history.md` §2 (already approved) scopes CareRequest's own auditable events to creation/conversion/authorization/idempotency/rate-limit/attachment outcomes — administrative read access is not among them, and §7 explicitly forbids introducing a Fase-5-specific audit mechanism.
- `CLAUDE.md` places "auditoría" under Fase 6's scope. Building an admin-read-audit hook now, only for `CareRequest`, would be an isolated exception inconsistent with every other clinical `ModelAdmin` in the project, not a fix that closes the actual gap (which is project-wide).

**Future owner:** Fase 6 (Notificaciones y auditoría). **Missing evidence for that future work:** a generic mechanism to call `safe_record_event` from a `ModelAdmin` read path (no such hook exists yet anywhere in the project); a decision on whether it applies retroactively to the existing clinical admins listed above or only to newly registered ones; possibly new `AuditEvent.Action`/`ResourceType` values for `CareRequest` if the existing enum is extended (matching the precedent already set when Fase 4 added its own actions/resource types to the same `AuditEvent` model, `ADR-021`).

**Risk accepted, not new:** until Fase 6 closes this, an administrator's read of `CareRequest.motivo`/`padecimiento`/`descripcion` via `/admin/` leaves no audit trail — identical to the pre-existing, already-known state of every other clinical entity's admin in this project (tracked as an open item in `ADR-004-role-and-object-permissions.md` §39). This is not a risk introduced by Fase 5. Partial mitigation already in place: the admin surface is read-only (no write path exists to compound the gap with unaudited mutation).
