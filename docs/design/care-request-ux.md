# CareRequest — UX Design

## 1. Purpose

Define the user experience for requesting an appointment through CareRequest while preserving the approved domain and Agenda rules.

The UX must remain deliberately simple. CareRequest is not a workflow for clinical review; it is a direct appointment request that is converted immediately when the selected slot remains valid.

## 2. Primary flow

The authenticated user:

1. selects the doctor;
2. selects the clinic/context when applicable;
3. selects a date;
4. selects an available slot generated by Agenda;
5. enters the required request information;
6. optionally adds additional free-text information and attachments;
7. confirms the request.

The selected slot provides the already-defined `start` and `end` values.

The client does not calculate the end time.

## 3. Required and optional information

Required:

- doctor;
- clinic;
- selected slot;
- motivo.

The patient and actor context are derived from the authenticated user and authorization context.

Optional:

- responsible when the actor is acting as a responsible party;
- padecimiento;
- descripcion;
- attachments.

The UI must make required fields visibly distinguishable.

## 4. Slot selection

Slots are obtained from the existing Agenda availability flow.

The UI should preserve the selected slot's start/end values rather than reconstructing them from a clock time.

The server remains authoritative: the selected interval is revalidated by Agenda when the Hold is created.

A slot becoming unavailable between display and submission is therefore a normal business outcome, not a UI error.

## 5. Confirmation

The confirmation action submits exactly one CareRequest creation operation.

The UI must avoid generating duplicate submissions through accidental double-clicks or repeated taps. Backend idempotency remains the authoritative protection.

## 6. Success

A successful operation results in:

- CareRequest status `CONVERTIDA`;
- one Appointment;
- zero or more ClinicalDocuments associated with that Appointment.

The UI should present the appointment result using the returned DTO and should not require a separate refresh-driven conversion workflow.

## 7. Failure

If Agenda rejects the selected interval or another transaction-critical operation fails:

- no pending CareRequest remains;
- no partial Appointment is presented as created;
- the user receives a clear actionable error;
- the user can return to slot selection when availability has changed.

CareRequest is not a waiting queue.

## 8. Idempotent replay

When a request is retried with the same `Idempotency-Key`, the UI should treat the returned result as the result of the original operation.

The UI does not need a special second workflow for replay.

## 9. Rate limiting

When the authenticated actor reaches the configured 3-per-hour creation limit and the request is not an idempotent replay, the UI should show a concise rate-limit message and avoid suggesting that the request has been queued.

## 10. Attachments

The UI should support up to 5 files per request.

Each file must comply with the approved type and size constraints.

The user should see validation feedback before submission whenever possible, while the server remains authoritative.

**Implemented (2026-09-18):** see `care-request-screens.md` §10 for the full detail — count,
extension, and size are validated client-side before submission, using the server's own
constants, and the server independently re-validates all of them (unchanged).

## 11. No clinical interpretation

The UX must not present:

- automated diagnosis;
- triage result;
- urgency classification;
- treatment recommendation.

The request fields are collected as free text and handled as provided.

## 12. Accessibility and design-system reuse

Use the existing Design System and UI Guidelines.

Do not create a Fase 5-specific visual language.

Error, focus, disabled, loading, and validation states should follow the existing project conventions.
